# Multiplayer WebSocket Data Protocol

## General Rules

- Use JSON messages over WebSocket.
- Every message must contain `type` and `payload`.
- Use camelCase for property names.
- Use event names in `category:action` format.
- All player IDs are generated by the backend.
- All positions use Three.js coordinates (`x`, `y`, `z`) in world units.
- Rotation is in radians around the Y axis.
- Never transmit Blender models, textures, or binary assets through WebSocket.
- Maximum 5 players in one shared room.
- **The frontend is authoritative for player movement, rotation, animation, and collision detection.**
- **The backend must NOT calculate player movement, physics, or collisions.**
- The backend manages player identities, connections, appearance, and the latest reported player states.
- Validate incoming message structures and numeric values before processing them.
- Unknown message types and invalid payloads must be handled safely.
- Do not change the protocol without updating both frontend and backend.

## Shared Data Types

The backend supports `custom`, `person2`, and `ceo` selection. See [CHARACTER_SELECTION.md](CHARACTER_SELECTION.md) for validation, rendering requirements and coordinated frontend rollout.

```ts
export type Appearance = {
  shirt: 0 | 1 | 2;
  pants: 0 | 1;
  hairstyle: 0 | 1;
  glasses: 0 | 1;
};

export type Vector3 = {
  x: number;
  y: number;
  z: number;
};

export type AnimationState = 'Idle' | 'Walk' | 'Run';

export type CharacterSelection =
  { model: 'custom'; appearance: Appearance } | { model: 'person2' | 'ceo'; appearance: null };

export type PlayerJoinPayload = { name: string } & CharacterSelection;

export type PlayerState = {
  id: string;
  name: string;
  position: Vector3;
  rotation: number;
  animation: AnimationState;
} & CharacterSelection;

export type PlayerMovement = {
  sequence: number;
  position: Vector3;
  rotation: number;
  animation: AnimationState;
};
```

## Client → Server Events

### `player:join`

Sent once after character selection. `custom` requires valid appearance; `person2` and `ceo` require explicit `appearance: null`. Missing model normalizes to `custom` only with valid appearance. Null/unknown models and invalid combinations receive `INVALID_MESSAGE` without creating a player.

```json
{
  "type": "player:join",
  "payload": {
    "name": "Player1",
    "model": "custom",
    "appearance": {
      "shirt": 1,
      "pants": 0,
      "hairstyle": 1,
      "glasses": 0
    }
  }
}
```

The backend validates the appearance, assigns the player ID and initial spawn position, and stores the player.

### `player:move`

Sent when the player's position, rotation, or animation changes.

The frontend calculates the movement and sends the resulting state.

```json
{
  "type": "player:move",
  "payload": {
    "sequence": 42,
    "position": {
      "x": 10.5,
      "y": 0,
      "z": 4.2
    },
    "rotation": 1.57,
    "animation": "Run"
  }
}
```

Rules:

- The frontend calculates the player's position using Three.js.
- The frontend handles movement speed, collisions, and animations.
- Send the latest position, rotation, and animation.
- `sequence` must increase for each movement update within a session.
- The backend validates the message structure and checks that numeric values are finite and within configured world bounds.
- The backend rejects stale sequence numbers.
- The backend stores the latest accepted state without recalculating movement.
- The backend broadcasts the accepted state to other players.
- Do not send movement updates when nothing has changed.
- Send updates at a maximum of 20 times per second initially.
- Send a final `Idle` update when the player stops moving.

## Server → Client Events

### `world:init`

Sent only to the joining player after successful validation.

```json
{
  "type": "world:init",
  "payload": {
    "playerId": "player-123",
    "players": [
      {
        "id": "player-123",
        "name": "Player1",
        "model": "custom",
        "appearance": {
          "shirt": 1,
          "pants": 0,
          "hairstyle": 1,
          "glasses": 0
        },
        "position": { "x": 0, "y": 0, "z": 0 },
        "rotation": 0,
        "animation": "Idle"
      }
    ]
  }
}
```

The `players` array includes the joining player and all existing players. Every full PlayerState includes normalized model and appearance, including `player:joined` and non-null `vehicle:released.payload.player`. Selection remains fixed until disconnect; reconnect validates a new selection and assigns a fresh ID.

### `player:joined`

Broadcast to existing players when someone successfully joins.

```json
{
  "type": "player:joined",
  "payload": {
    "player": {
      "id": "player-456",
      "name": "Player2",
      "model": "custom",
      "appearance": {
        "shirt": 2,
        "pants": 1,
        "hairstyle": 0,
        "glasses": 1
      },
      "position": { "x": 2, "y": 0, "z": 3 },
      "rotation": 0,
      "animation": "Idle"
    }
  }
}
```

### `player:update`

Broadcast by the backend to other players after receiving a valid `player:move` message.

```json
{
  "type": "player:update",
  "payload": {
    "id": "player-456",
    "sequence": 42,
    "position": {
      "x": 10.5,
      "y": 0,
      "z": 4.2
    },
    "rotation": 1.57,
    "animation": "Run"
  }
}
```

Rules:

- The backend assigns the `id` from the authenticated WebSocket session.
- The backend must not trust a client-supplied player ID.
- The backend forwards the accepted position, rotation, and animation without calculating new values.
- The backend broadcasts updates to other joined players, excluding the sender.
- The frontend ignores stale or out-of-order sequence numbers.
- Remote players use interpolation for smooth movement.

### `player:left`

Broadcast when a player disconnects or leaves.

```json
{
  "type": "player:left",
  "payload": {
    "id": "player-456"
  }
}
```

### `server:error`

Sent when a request cannot be processed.

```json
{
  "type": "server:error",
  "payload": {
    "code": "ROOM_FULL",
    "message": "Maximum 5 players allowed."
  }
}
```

Other error codes may include:

- `INVALID_MESSAGE`
- `INVALID_APPEARANCE`
- `INVALID_POSITION`
- `ALREADY_JOINED`
- `NOT_JOINED`
- `RATE_LIMITED`

## Synchronization Rules

### Frontend Responsibilities

- Calculate the local player's position (`x`, `y`, `z`).
- Calculate rotation and animation state.
- Handle keyboard input, movement speed, gravity, and collision detection.
- Prevent movement through walls, buildings, and other solid objects.
- Send `player:move` when movement state changes.
- Limit movement updates to approximately 20 per second.
- Render the local player immediately without waiting for server confirmation.
- Interpolate remote player positions and rotations.
- Apply remote animation states.
- Do not allow appearance changes after joining.
- Do not send GLB models or textures through WebSocket.

### Backend Responsibilities

- Manage WebSocket connections and player sessions.
- Enforce the maximum of 5 players.
- Generate unique player IDs.
- Validate appearance during `player:join`.
- Store the latest accepted position, rotation, and animation.
- Validate movement payload structure and finite numeric values.
- Reject stale sequence numbers and excessive message rates.
- Optionally enforce configured world-coordinate bounds.
- Broadcast accepted player updates to other joined players.
- Remove disconnected players and broadcast `player:left`.
- Do not calculate movement, gravity, physics, or collisions.
- Do not modify reported movement values except to reject invalid updates.
- Do not run a game simulation tick loop.
- Do not introduce a physics engine on the backend.

### Network Performance

- Use event-driven WebSocket messages.
- Movement updates should be limited to 20 messages per second per player.
- Do not broadcast unchanged player states.
- Do not include model or appearance in movement messages. Extra selection fields are discarded and cannot change stored selection.
- Do not send complete world state on every update.
- Use WebSocket ping/pong to detect disconnected clients.
- Prevent excessive queued messages for slow connections.

## Vehicle Protocol Extension

The backend contract is implemented by the frontend message types, validation, driving controls, and rendering. Automated transport tests verify the wire messages; live backend/browser integration still requires verification. Existing walking and chat messages remain unchanged.

### Shared Configuration

The backend exports `vehicleConfig` from its `src/vehicle.ts`; the frontend uses the same bounds and limits in `src/network/protocol.ts` and `src/vehicles/VehicleController.ts`:

```ts
const vehicleConfig = {
  id: 'cybertruck-1',
  spawn: {
    position: { x: -35, y: 0, z: 0 },
    rotation: Math.PI / 2,
  },
  worldBounds: {
    min: { x: -70, y: -2, z: -70 },
    max: { x: 72, y: 25, z: 70 },
  },
  minSpeed: -4,
  maxSpeed: 10,
  maxAbsSteering: Math.PI / 6,
  enterRadius: 3,
  exitRadius: 3,
};
```

Bounds and limits are inclusive. Radii use three-dimensional Euclidean distance. These bounds apply to vehicle movement and proposed exit positions; walking retains its existing finite-coordinate validation. Vehicle movement has its own rolling 20-request-per-second window, separate from walking. Enter and exit share a rolling 2-request-per-second window. Structurally valid vehicle attempts count even when rejected; requests beyond the limit do not extend the window. Walking sequences and chat cooldowns remain independent. Malformed vehicle payloads receive `INVALID_MESSAGE`; valid but out-of-range movement receives `INVALID_VEHICLE_STATE` and out-of-range exits receive `INVALID_EXIT_POSITION`.

### Authority and Shared State

- There is one shared vehicle, `cybertruck-1`, with one driver and no passengers.
- The backend owns occupancy and serializes enter, exit, movement, and disconnect handling per vehicle. Never grant the same seat to two players.
- The driver frontend calculates vehicle movement, acceleration, braking, steering, and collisions. The backend validates and stores reports without running physics or simulation ticks, following the existing player movement architecture.
- Resolve the sender from the joined WebSocket session. Never accept a client-supplied driver ID.
- The backend initializes the vehicle from shared world configuration matching the GLB placement. Do not use example coordinates below as the actual spawn.
- Position is the world-space position of the `Cybertruck • drive control` pivot; rotation is its world Y heading in radians. Clients must account for its `Cybertruck • placement` parent when applying transforms. Apply no additional scale or pitch/roll through this protocol.

```ts
export type VehicleState = {
  id: 'cybertruck-1';
  driverId: string | null;
  revision: number;
  position: Vector3;
  rotation: number;
  speed: number;
  steering: number;
  wheelAngle: number;
};

export type VehicleMovement = {
  vehicleId: 'cybertruck-1';
  revision: number;
  sequence: number;
  position: Vector3;
  rotation: number;
  speed: number;
  steering: number;
  wheelAngle: number;
};
```

`speed` is signed world units per second (positive forward, negative reverse). `steering` is the front-wheel angle in radians, positive for a left turn. `wheelAngle` is a cumulative, unwrapped wheel-spin angle in radians, positive for forward rolling; clients map that sign to each wheel's local axle. Interpolate this angle directly to avoid losing full turns. Do not play the prerecorded truck translation clip while driving, or advance the wheel-spin clips independently of vehicle movement.

`revision` is a backend-generated nonnegative safe integer, initially zero, incremented for every accepted occupancy transition or disconnect release. It identifies the current driving lease. `sequence` is a nonnegative safe integer, increasing within that lease; start at zero when a new driver is granted control. Reset the backend's last accepted vehicle sequence on each new revision. Vehicle and walking sequences are independent.

### Initialization and Entering

Extend `world:init.payload` with `vehicles: VehicleState[]`, containing exactly the shared Cybertruck and its latest accepted state. Include occupied vehicles for late joiners. The existing `players` array still includes drivers; occupancy is derived from `driverId`, without changing `PlayerState` or adding a seated animation value. While occupied, keep the driver's stored player position at the vehicle pivot, rotation at its heading, and animation at `Idle`. Render the driver at a configured seat offset or hide their standing mesh; disable their walking controls.

Pressing E near the vehicle sends:

```json
{
  "type": "vehicle:enter",
  "payload": { "vehicleId": "cybertruck-1", "revision": 0 }
}
```

The backend requires a joined player, a matching current revision, an empty seat, and a player not already driving. Check the distance between the latest stored player feet position and vehicle pivot against a configured enter radius (initially 3 world units). This is a proximity check, not collision simulation. Check and assign occupancy atomically, increment the revision, set speed and steering to zero, update the stored driver player transform, and broadcast `vehicle:occupied` to all joined clients, including the requester:

```json
{
  "type": "vehicle:occupied",
  "payload": {
    "vehicle": {
      "id": "cybertruck-1",
      "driverId": "player-123",
      "revision": 1,
      "position": { "x": 10, "y": 0, "z": 4 },
      "rotation": 0,
      "speed": 0,
      "steering": 0,
      "wheelAngle": 0
    }
  }
}
```

Only start driving after this grant. A rejected enter leaves occupancy unchanged. Repeated requests with an old revision cannot grant control again.

### Driving Updates

WASD controls acceleration/reverse and steering locally. Send changed state at a maximum of 20 Hz using the existing socket:

```json
{
  "type": "vehicle:move",
  "payload": {
    "vehicleId": "cybertruck-1",
    "revision": 1,
    "sequence": 12,
    "position": { "x": 10, "y": 0, "z": 6 },
    "rotation": 0.1,
    "speed": 4,
    "steering": 0.15,
    "wheelAngle": 5.5
  }
}
```

- Require the session player to be the current driver and `revision` to match the current lease. Reject stale or duplicate sequences without changing stored state.
- Validate every numeric field as finite, sequences/revisions as nonnegative safe integers, position against configured world bounds, and speed/steering against shared configured vehicle limits. Frontend and backend must agree on those limits before rollout; they are configuration values, not client-provided fields.
- Store the accepted vehicle state and update the stored driver's player transform to match. Do not broadcast separate `player:update` messages for driving.
- Broadcast `vehicle:update` to all joined clients, including the driver. Its payload is `{ vehicle: VehicleState, sequence: number }`; the sequence is copied from the accepted movement report and the revision comes from server state.
- Clients ignore updates with older revisions or non-increasing sequences within a revision. An update with an unrecognized newer revision requires resynchronization through a fresh join rather than assuming control. Occupancy transitions establish the revision and reset interpolation history.
- Remote clients interpolate vehicle transforms, steering, and wheel angle. The driver renders immediately and uses accepted echoes as acknowledgements. A vehicle echo must not rewind newer local prediction.
- Stop sending `player:move` while driving; the backend rejects it with `PLAYER_DRIVING`. Do not advance the walking sequence for vehicle updates.
- Send a final vehicle state with `speed: 0` when stopped, then send nothing until state changes. Wheel spin stops with the vehicle.

### Exiting

Pressing E while driving brakes to a stop and collision-checks a nearby exit location. The frontend freezes its stopped prediction, sends the final stopped `vehicle:move`, waits for the matching `vehicle:update` acknowledgement with `speed: 0`, and then sends:

```json
{
  "type": "vehicle:exit",
  "payload": {
    "vehicleId": "cybertruck-1",
    "revision": 1,
    "position": { "x": 12, "y": 0, "z": 6 },
    "rotation": 0.1
  }
}
```

Require the current driver, matching revision, and latest accepted speed equal to zero. Validate the proposed player feet position and heading as finite, the position within world bounds, and its distance from the stored vehicle pivot within a configured exit radius (initially 3 world units). The frontend must find solid, unobstructed ground outside the vehicle; if none is available, stay seated. The backend performs numeric/proximity checks only, consistent with frontend-owned collisions.

Atomically release the seat, increment the revision, keep the vehicle at its last accepted position with speed and steering zero, and set the player's stored transform to the accepted exit location with animation `Idle`. Broadcast to everyone, including the driver:

```ts
type VehicleReleasedPayload = {
  vehicle: VehicleState; // driverId is null; revision is incremented.
  player: PlayerState; // Former driver at the accepted exit position, Idle.
  reason: 'exit';
};
// Envelope: { type: "vehicle:released", payload: VehicleReleasedPayload }
```

Apply the release atomically on clients: update the vehicle, place/show the player, then re-enable their walking controls. Do not resume walking before confirmation. Continue the existing walking sequence; do not reset it on exit. Rejection leaves the player seated and the lease intact.

### Disconnects, Errors, and Recovery

- On driver disconnect or heartbeat timeout, atomically clear occupancy, increment the revision, and stop the truck at its latest accepted transform with speed and steering zero. Preserve wheel angle. Broadcast `vehicle:released` with `{ vehicle, player: null, reason: "disconnect" }` before `player:left`. No exit position is needed because the player is removed.
- A reconnect creates a fresh player session and receives current vehicle state in `world:init`. Never restore driving privileges from an old player ID or revision. Keep the parked vehicle in memory while the backend runs, including when the room becomes empty; a backend restart resets it to configured spawn.
- Use `server:error` for rejection, adding optional `requestType`, `vehicleId`, and `revision` fields to its existing payload. `revision`, when present, is the current server revision. Keep `code` and `message` mandatory. Rejections do not disconnect an otherwise valid session or mutate vehicle/player state.
- Vehicle error codes: `VEHICLE_NOT_FOUND`, `VEHICLE_OCCUPIED`, `ALREADY_DRIVING`, `VEHICLE_TOO_FAR`, `NOT_VEHICLE_DRIVER`, `STALE_VEHICLE_REVISION`, `STALE_VEHICLE_SEQUENCE`, `INVALID_VEHICLE_STATE`, `VEHICLE_MOVING`, `INVALID_EXIT_POSITION`, and `PLAYER_DRIVING`. Existing `NOT_JOINED`, `INVALID_MESSAGE`, and `RATE_LIMITED` also apply.
- Rate-limit enter/exit requests separately from movement (initially 2 combined requests per second per session). Reject excessive vehicle movement above 20 Hz using the same policy as walking. Do not create another room, socket, or backend physics loop.
- Verify simultaneous enter requests, unauthorized movement/exit, duplicate sequences, old-lease updates, stopping, blocked exits, late joining, driver disconnect, reconnect, and continued walking after exit. Confirm every client sees exactly one truck and one occupant at most.

## Chat Protocol Compatibility

Keep the existing multiplayer chat protocol unchanged.

- `chat:send`: Client sends text to the backend.
- `chat:message`: Backend broadcasts accepted messages.
- Chat uses the same WebSocket connection.
- Chat is independent of movement updates.
- Chat messages must be validated and rate-limited.

## Shared Frame Picture HTTP API

The proposed upload-and-replace API is specified in [FRAME_PICTURES.md](FRAME_PICTURES.md). Implement `GET /api/frame-pictures`, `PUT /api/frame-pictures/:frameId` using multipart field `image`, and versioned JPEG/MP4 downloads. The additive video extension uses the same multipart field `image`, with `mediaType: "video"` and a versioned video path in the legacy `imageUrl` response field. Both `left` and `right` are shared across all visitors; any visitor may upload. Persist files and revisions on durable storage. The initial contract uses HTTP polling and adds no WebSocket events or `world:init` fields. The frontend uses this HTTP contract; the separate backend must implement it before shared uploads work.

## Protocol Compliance

- Both frontend and backend MUST follow this document.
- Use `type` and `payload`, never `event` and `data`.
- Replace the old `player:input` event with `player:move`.
- Remove the old `MovementInput` type.
- Remove server-side movement calculations and movement simulation ticks.
- Remove `lastProcessedInput` because the server no longer calculates movement from inputs.
- Keep `sequence` for ordering movement updates.
- Keep appearance customization restricted to before joining.
- Update both applications whenever this protocol changes.
- Add automated tests for message parsing, validation, and broadcasting.
- Never claim protocol compliance without verifying actual message structures.
