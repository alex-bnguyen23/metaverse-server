# Shared frame picture API protocol

## Status and scope

This document specifies the HTTP API implemented by this Node.js backend. The frontend `FramePictures.ts` must be updated separately to use these endpoints; frontend integration is not included in this repository.

## Backend implementation and configuration

- `src/routes/frame-pictures.ts` wires the three HTTP endpoints into Express.
- `src/middlewares/image-upload.ts` handles Multer memory uploads, multipart validation, byte limits, rate/concurrency limits, and JSON errors.
- `src/controllers/frame-pictures.ts` handles HTTP responses and delegates image processing and storage to `src/services/frame-pictures.ts`.
- Multer accepts exactly one `image` file up to 10 MiB. Sharp validates decoded content and generates the normalized JPEG asynchronously. Multipart transfer has a 30-second timeout and JPEG processing has a 15-second decoder timeout.
- Set `FRAME_PICTURES_DIR` to persistent storage in production. Local development defaults to `data/frame-pictures` inside the project, which is ignored by Git. Use a single server instance. Windows does not support the POSIX directory flush used for durable renames; production durability assumes a POSIX persistent filesystem.
- Set `FRONTEND_ORIGINS` to a comma-separated list of allowed frontend origins, for example `http://localhost:5173,https://game.example.com`. Cross-origin access to this API is disabled unless configured. Existing unrelated HTTP routes retain their CORS behavior.
- Express proxy trust remains disabled by default. Configure only known trusted proxy addresses in `src/app.ts` for the deployment before relying on per-visitor IP limits behind a proxy.
- Metadata operations share one in-process queue. Storage reads clean temporary files, orphan images and older revisions after 60 seconds while retaining the current and immediately previous images. A crash-created orphan at the next revision can temporarily block replacements until this grace period expires. Malformed/missing committed metadata fails closed.
- `npm test` includes HTTP upload, normalization, rejection, rate-limit, persistence, and concurrent commit checks. Frontend behavior and deployment-level crash recovery still require integration verification.

Any visitor may upload or replace either picture. Both frames belong to the one shared world, independent of player sessions and the five-player room limit. Everyone loads the latest committed image. No Firebase, database, new room, or additional WebSocket connection is required.

Uploads and image downloads use HTTP. Never send files, base64 images, textures, or GLB geometry through WebSocket. Existing player, vehicle, chat, and `world:init` payloads remain unchanged. Use HTTP polling for shared artwork updates in this initial version.

## Frame identifiers and data types

Only `left` and `right` are valid frame IDs. Map these to the GLB objects whose `userData.name` is `Jinja picture stand • left` and `Jinja picture stand • right`. Their picture children have `userData.name` equal to `Picture • 1920x1080`.

```ts
export type FrameId = 'left' | 'right';

export type FramePicture = {
  frameId: FrameId;
  revision: number;
  imageUrl: string | null;
  updatedAt: number | null;
};

export type FramePicturesResponse = {
  frames: [FramePicture, FramePicture]; // Always left, then right.
};

export type FramePictureResponse = {
  frame: FramePicture;
};

export type FramePictureError = {
  error: {
    code: string;
    message: string;
  };
};
```

`revision` is a backend-generated nonnegative safe integer, persisted separately for each frame. Initially it is zero, with `imageUrl: null` and `updatedAt: null`; clients then show the original embedded GLB artwork. Each successful replacement increments that frame's revision by one. `updatedAt` is the backend's Unix timestamp in milliseconds. Clients must not supply these fields.

`imageUrl` is a root-relative path on the API origin, generated by the backend, such as `/api/frame-pictures/left/images/1.jpg`. Resolve it against the configured HTTP API origin, not the frontend origin or the WebSocket URL. Never return a local disk path or a URL derived from an uploaded filename.

## HTTP endpoints

### GET /api/frame-pictures

Public read endpoint. Return `200 OK`, `Content-Type: application/json`, and `Cache-Control: no-store` with exactly two entries:

```json
{
  "frames": [
    {
      "frameId": "left",
      "revision": 1,
      "imageUrl": "/api/frame-pictures/left/images/1.jpg",
      "updatedAt": 1793059200000
    },
    {
      "frameId": "right",
      "revision": 0,
      "imageUrl": null,
      "updatedAt": null
    }
  ]
}
```

Read both records from one consistent committed metadata snapshot. A frame without an upload is a valid empty record, not a 404. If committed metadata cannot be read, return `503 STORAGE_UNAVAILABLE` rather than silently resetting revisions.

### PUT /api/frame-pictures/:frameId

Public upload-and-replace endpoint. No login or joined WebSocket session is required in this initial version. Any visitor can replace either frame, as requested. Apply the same file validation and rate limits to all visitors.

Request: `multipart/form-data` containing exactly one file field named `image`. Do not accept extra files or form fields. The browser must generate the multipart boundary; do not manually set the `Content-Type` header when sending `FormData`.

```ts
const form = new FormData();
form.append('image', file);
const response = await fetch(`${apiOrigin}/api/frame-pictures/left`, {
  method: 'PUT',
  body: form,
});
```

Successful response: `200 OK`, `Content-Type: application/json`, `Cache-Control: no-store` and `{ "frame": FramePicture }`:

```json
{
  "frame": {
    "frameId": "left",
    "revision": 2,
    "imageUrl": "/api/frame-pictures/left/images/2.jpg",
    "updatedAt": 1793059260000
  }
}
```

The same endpoint creates the first image and replaces later images. Commit the file and metadata durably before returning success. The response describes the committed revision; another upload may supersede it immediately afterward. Failed requests must leave the previous committed picture unchanged. A lost response may still correspond to a committed upload: refetch metadata before retrying. Upload retries are not idempotent and may create another revision.

### GET /api/frame-pictures/:frameId/images/:revision.jpg

Serve the backend-generated JPEG for a committed revision. Accept only a valid frame ID and a positive safe integer revision; never treat route parameters as arbitrary paths. Return `Content-Type: image/jpeg`, `X-Content-Type-Options: nosniff`, and `Cache-Control: public, max-age=31536000, immutable`. The URL always identifies the same bytes; never overwrite an existing revision's file.

Return `404 IMAGE_NOT_FOUND` if that revision is unavailable. Retain the current image and at least the immediately previous committed revision per frame to accommodate in-flight metadata reads. Older revisions may be deleted after a grace period of at least 60 seconds. Clients encountering a missing old revision refetch metadata and load the current URL. This is a current-picture feature, not permanent upload history.

## Server validation and limits

- Allow only JPEG, PNG and WebP input. Check decoded content as well as declared MIME type; do not trust extensions, filenames or headers alone. Reject SVG, HTML, animated images, malformed files and unsupported formats.
- Limit the uploaded file to 10 MiB (10,485,760 bytes). Enforce a streaming request limit of 11 MiB including multipart overhead, and abort oversized requests early. Reject zero-byte files, duplicate `image` fields, extra fields, extra files and malformed multipart bodies.
- Limit decoded images to 20 million pixels and a maximum of 8192 pixels on either axis. Enforce decoder resource limits and a request timeout; input byte size alone does not bound decoded memory.
- Apply EXIF orientation, then fit the full image into a 1280 by 720 canvas with a `#151515` background. Preserve aspect ratio, without cropping or stretching. Encode a new JPEG at quality 85 and strip metadata. Never serve the original uploaded file.
- Initially allow 5 upload attempts per rolling 60 seconds per client IP, shared across both frames. Count rejected attempts too; requests already beyond the limit do not extend the window. Return `429` with `Retry-After` in whole seconds. Configure trusted proxy handling for the deployment; do not trust arbitrary forwarded IP headers.
- Limit active upload processing to 2 requests per server instance; return `503 UPLOAD_BUSY` with `Retry-After: 2` when full. Do not let image decoding block multiplayer message handling; use an asynchronous image-processing library or worker.
- Do not accept user-supplied URLs, file paths, frame names beyond the two IDs, player IDs, revisions or timestamps. Bound and sanitize error messages; never expose stack traces or server paths.

## Errors

All API errors use the `FramePictureError` JSON shape and `Cache-Control: no-store`. HTTP errors do not use WebSocket `server:error` and must not disconnect players.

| HTTP status | Code                   | Meaning                                                              |
| ----------- | ---------------------- | -------------------------------------------------------------------- |
| 400         | INVALID_UPLOAD         | Missing/extra fields, missing/empty file or malformed multipart body |
| 400         | INVALID_IMAGE          | Corrupt, animated or undecodable image                               |
| 404         | FRAME_NOT_FOUND        | Frame ID is neither left nor right                                   |
| 404         | IMAGE_NOT_FOUND        | Invalid or unavailable image revision                                |
| 413         | FILE_TOO_LARGE         | File or total request exceeds the byte limit                         |
| 413         | IMAGE_TOO_LARGE        | Decoded dimensions exceed the limits                                 |
| 415         | UNSUPPORTED_IMAGE_TYPE | Input is not JPEG, PNG or WebP                                       |
| 429         | RATE_LIMITED           | Upload rate exceeded; include Retry-After                            |
| 503         | UPLOAD_BUSY            | Concurrent processing limit reached; include Retry-After             |
| 503         | STORAGE_UNAVAILABLE    | Storage read/write or durable commit failed                          |

Example:

```json
{
  "error": {
    "code": "FILE_TOO_LARGE",
    "message": "Choose an image up to 10 MiB."
  }
}
```

## Persistence, concurrent replacements and Render deployment

Use one backend instance with durable local storage for this initial design. Configure an absolute `FRAME_PICTURES_DIR` inside the persistent disk mount, for example `/var/data/frame-pictures`. Store both metadata and generated JPEGs there. A JSON manifest is sufficient; no database is required. Temporary files must also stay on that disk so atomic renames use the same filesystem.

Serialize commits through one shared lock for the manifest, including uploads to different frames, to avoid one frame's update overwriting the other's metadata. Decode to a unique temporary file first. Under the lock, read the current manifest, allocate the next revision for the target frame, publish the completed JPEG, and atomically replace the manifest using a temporary file and rename. Flush file data and metadata as appropriate for durable storage. Only after commit release the lock and return success. The final committed upload wins when uploads race; never partially overwrite a visible JPEG.

Load the manifest on startup and preserve revisions across restarts and deployments. Initialize the two zero-revision records only for genuinely empty storage. Treat malformed metadata or missing current images as storage failures, not an empty world. Clean orphan temporary/unreferenced files after a grace period without deleting any current or retained previous image. If a crash occurs before metadata commit, the old record remains authoritative.

For Render, attach a persistent disk to the paid backend web service and point `FRAME_PICTURES_DIR` into its mount. Ordinary service files are ephemeral; free web services cannot provide durable local uploads. Deploy one instance when using this manifest/lock design. Scaling to multiple instances requires shared object storage and a coordinated metadata commit mechanism.

Serve the API and images over HTTPS in production. If frontend and backend origins differ, configure an explicit frontend origin allowlist for CORS, allow `GET`, `PUT` and `OPTIONS`, and allow the `Content-Type` header. Return CORS headers on image responses and errors too; expose `Retry-After` to browsers. Add `Vary: Origin` when dynamically selecting an allowed origin. No cookies or credentials are required by this anonymous contract. CORS is browser access control, not authentication.

## Frontend integration required after backend implementation

1. Configure `VITE_API_URL` as the HTTP(S) API origin, for example `https://your-backend.onrender.com`; use `http://localhost:3000` for local development. Keep it separate from `VITE_WS_URL` and do not assume the frontend host serves the API.
2. Fetch `GET /api/frame-pictures` after world loading. Poll every 5 seconds while the page is visible, without overlapping requests; refetch immediately on page visibility restoration. Fetch regardless of WebSocket connection status. Retry transient failures on the next poll and keep the last valid artwork.
3. Validate response structures, frame IDs, safe-integer revisions, timestamps and API-origin image URLs. Apply only newer revisions per frame. Ignore stale poll/upload responses, and also guard asynchronous image decoding so a slower old download cannot replace a newer picture.
4. Upload the selected original file as `FormData` through the PUT endpoint, disabling only that frame's button until completion. On success, load the returned committed URL and refetch metadata. On errors, preserve the current image and show the server message. All visitors observe changes by the next successful poll, plus image download time; this version does not promise instant WebSocket delivery.
5. Stop using browser localStorage as the artwork source. Never auto-upload old `osaka-frame-v1-left` or `osaka-frame-v1-right` data; those personal choices must not overwrite shared artwork on join. A zero revision displays the original GLB artwork.
6. Keep separate cloned materials for the two picture meshes. Use sRGB textures and the GLTF UV orientation (`flipY: false`), configure anonymous cross-origin image loading, and dispose replaced textures. Preserve original shared GLB resources for scene cleanup.
7. Abort fetches, cancel poll timers/listeners and ignore pending image loads on unmount. Keep network traffic and texture updates independent of React's animation loop. Never reload the full GLB to update artwork.

## Backend acceptance checks

- Empty storage returns both zero-revision records and no image URLs.
- An anonymous upload creates left revision 1; another replaces it with revision 2; right stays unchanged. Visitors do not need a player slot to use the API.
- Two clients read identical committed metadata and image bytes. A late visitor and a reconnected client load the latest version. The frontend sees a change within one successful polling interval plus download time.
- Parallel uploads to the same frame receive distinct increasing revisions; parallel uploads to different frames preserve both records.
- Rejected, oversized and interrupted uploads preserve the existing image. Spoofed MIME types, invalid IDs, traversal attempts, extra fields/files, oversized decoded images and animated inputs are rejected.
- Rate limits, concurrency limits, Retry-After headers and cross-origin requests behave as specified without interrupting multiplayer.
- Restart/redeploy with the persistent disk: both images, timestamps and revisions survive. Simulate commit failure/crash: readers receive a complete old or new record, never a partially written file.
- Versioned URLs do not return stale overwritten content. A missing old image triggers metadata refresh; cleanup preserves current and immediately previous images.

Backend implementation and frontend integration must each be tested before describing this contract as supported.
