## Multiplayer Chat Protocol

The game supports real-time text chat between players in one shared room.

### General Rules

- Maximum 5 players in one room.
- All connected and joined players can send and receive chat messages.
- Use the existing WebSocket connection at `/`.
- Do not create a separate WebSocket connection for chat.
- Use the standard message envelope: `{ "type": "...", "payload": { ... } }`.
- The backend is authoritative for chat messages.
- The frontend must never assign sender IDs or timestamps.
- Only players who successfully joined the world can send messages.
- Broadcast accepted chat messages to all joined players, including the sender.
- Store chat messages in memory only if chat history is needed.
- Do not introduce a database for chat.
- Never broadcast unvalidated user input.

### Chat Data Types

```ts
export type ChatMessage = {
  id: string;
  senderId: string;
  senderName: string;
  text: string;
  timestamp: number;
};

export type ChatSendPayload = {
  text: string;
};
```

- `id`: Unique message ID generated by the backend.
- `senderId`: Player ID assigned by the backend.
- `senderName`: Player name from the server's player state.
- `text`: Validated chat message.
- `timestamp`: Server-generated Unix timestamp in milliseconds.

### Client → Server

#### `chat:send`

Sent when a player submits a chat message.

```json
{
  "type": "chat:send",
  "payload": {
    "text": "Hello everyone!"
  }
}
```

The client must not send `senderId`, `senderName`, or `timestamp`.

### Server → Client

#### `chat:message`

Broadcast to all joined players, including the sender.

```json
{
  "type": "chat:message",
  "payload": {
    "id": "msg-123",
    "senderId": "player-123",
    "senderName": "Player1",
    "text": "Hello everyone!",
    "timestamp": 1792720000000
  }
}
```

### Chat Validation Rules

- Accept only string messages.
- Trim leading and trailing whitespace.
- Reject empty or whitespace-only messages.
- Maximum message length: 200 Unicode code points.
- Limit each player to 1 accepted message per second.
- Reject messages from players who have not joined.
- Generate message IDs and timestamps on the backend.
- Do not trust sender information supplied by clients.
- Reject invalid messages safely without crashing the server.
- Use the existing `server:error` protocol for rejected messages.

### Frontend Rules

- Display messages in chronological order.
- Show the sender's name and message text.
- Display the local player's messages only after receiving `chat:message` from the server.
- Do not duplicate messages when the sender receives their own broadcast.
- Use message IDs as unique keys.
- Render messages as plain text, never as raw HTML.
- Limit retained messages in frontend memory to the latest 100.
- Disable chat sending until `world:init` has been received.
- Handle disconnections and failed messages gracefully.
- Keep chat state separate from Three.js rendering state.
- Do not interfere with character movement when the chat input is focused.

### Backend Rules

- Handle `chat:send` using the existing WebSocket server.
- Validate the sender's active session.
- Validate and rate-limit the message.
- Generate the message ID using `crypto.randomUUID()`.
- Generate the timestamp using `Date.now()`.
- Retrieve the sender's name and ID from server-side player state.
- Broadcast `chat:message` to every joined player.
- Keep chat processing separate from movement synchronization.
- Do not include chat messages in the 20 TPS game loop.
- Do not log full chat message contents by default.
- Add meaningful English comments explaining validation, rate limiting, and broadcasting.

### Error codes

Invalid chat payloads receive `INVALID_MESSAGE`; sending before joining receives `NOT_JOINED`; sending within one second of the last accepted message receives `CHAT_RATE_LIMITED`. Rejections do not consume the chat cooldown. Payloads must contain only `text`. No chat history is retained on the backend.
